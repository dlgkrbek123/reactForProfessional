Backbonejs

MVC 패턴
- APP을 3가지 구성요소로 나누어 표현 (비즈니스 로직 / UI / 입력을 분리)

1. 모델: 데이터와 비즈니스 규칙을 담당, 뷰로부터 분리됨 (데이터의 출처)
2. 뷰: UI / 모델이 제공한 데이터를 표시하고 사용자 명령을 컨트롤러로 전송 (데이터를 소비하고 표현하는 인터페이스)
3. 컨트롤러: 모델과 뷰 사이의 인터페이스 (사용자 입력처리)

분리를 통해 좋아졌지만 한계에 부딪힘
- 복잡한 앱에서 컨트롤러가 비대해져 관리가 어렵다. 
- 양방향 데이터바인딩을 사용하는 경우 부작용이 발생하기 쉽다 (모델과 뷰의 sync가 안맞음)
- 3가지 요소의 강한 결합이 생길수 있다.

하지만 보일러 플레이트가 많고 자동 동기화/업데이트가 안되는 문제도 있었고,
이벤트 기반의 아키텍쳐로 관리가 어려워서 아쉬웠다.

Knockout
- Observable(데이터의 출처)과 binding(UI)을 작성하는 방법을 제공
- 반응형 라이브러리로 sync문제를 해결해줌
- MVC를 진화시킨 MVVM 디자인패턴을 사용한다.

모델
- 데이터 + 비즈니스 로직
- CRUD 담당 / DB or 서비스와 통신
- 모델은 뷰와 뷰모델을 인식못함

뷰
- UI
- 데이터를 표현하고 사용자 입력을 받음
- MVVM에서는 로직을 포함하지 않음

뷰모델
- 모델과 뷰의 인터페이스
- 뷰에 데이터와 명령을 제공함 / 명령패턴을 통해 사용자 입력을 처리
- 프레젠테이션 로직을 포함하여 모델의 데이터를 뷰에서 표현하기 쉽게 가공
- 뷰모델은 뷰를 인식못함

MVC랑 비슷하긴하지만
- MVC는 사용ㅇ자입력이 컨트롤러에서 관리되고 모델을 업데이트한 후 뷰가 동기화 되지만,
  MVVM은 뷰는 뷰모델에 바인딩되어 자동으로 동기화된다.
- MVC는 뷰와 컨트롤러의 결합이 강하나, MVVM에서 뷰모델은 어떤뷰와도 연결될 수 있어 느슨함
- 사용자 입력이 MVC에서는 컨트롤러에서 처리되고, MVVM에서는 뷰모델의 데이터바인딩/명령을 통해 처리됨

뷰모델을 생성하고 HTML요소를 거기에 바인딩하는 방식

리액트
- 컴포넌트 기반 아키텍쳐의 시작 
  => 선언적 추상화
  => how to -> what to show
- 단방향 데이터 바인딩

- 가상 DOM
  - 실제 DOM을 js 객체로 메모리에 표현하는 것
  - 재조정을 통해 실제 DOM에 반영됨
  - 직접 DOM 조작을 최소화
  - 전체가 아닌 변경된 부분만 업데이트하여 성능 개선
  
초기 렌더링시 가상 DOM 객체가 생성됨 (type, children, props)
재조정은 state/props 변경이후 가상DOM트리의 이전버전과 현재버전을 비교해 어느부분이 업데이트가 필요한지 결정하는 과정

immutablity (불변성)
- 리액트는 state에 대해 불변성을 강제한다.
- 불변성이란 메모리 영역에서 값의 변경이 불가능한것을 의미 (js primitive type)

리액트에서 강제하는 이유
- 리액트는 state/props의 변경을 감지하여 리렌더링하는 기준이 효율성/간결성을 위해 얕은 비교(주소값 비교)가 기준이기 떄문에, 
  불변성을 지키지 않고 객체의 값을 직접 수정하는 경우 변경을 감지할 수 없다. 
- 변경사항을 추적하기 용이하다.
- 상태가 변경되면 원래 있던 상태를 업데이트하지 않고 새로운 상태를 표현하는 새 객체를 반환

얕은 복사: 객체를 복사할떄 원래값과 복사된 값이 같은 참조를 가리키는 것
깊은 복사: 원래값과 복사된 값이 객체의 nesting이 있어도 참조가 끊김 (재귀, JSON.stringify, lodash 사용)

flux 아키텍쳐
- 단방향 데이터 흐름을 강조한 전역상태 관리
- action: 데이터 변경을 식별하기 위한 이벤트 객체
- store: 애플리케이션의 상태와 로직을 포함
- store에 action을 dispatch하여 상태가 변경되면 뷰에 바로 반영되는 단방향 흐름

state에 대한 단일 정보 출처를 제공함
